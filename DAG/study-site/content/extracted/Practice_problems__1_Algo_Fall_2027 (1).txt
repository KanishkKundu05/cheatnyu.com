1    BUBBLESORT (A , n )
2    1 for i = 1 to n - 1
3    2      for j = n downto i + 1
4    3           if A [ j ] < A [ j - 1]
5    4                 exchange A [ j ] with A [ j - 1]

Conventions (as in lecture): arrays are indexed from 1; A[i : j] means all entries from A[i] through
A[j] inclusive. For a loop for x = a to b, the loop-control line executes b − a + 2 times (that’s
b − a + 1 “true” tests plus one final “false” test), while the loop body executes b − a + 1 times.
Loop invariant (Lecture 1): at the start of each outer-loop iteration, A[1 : i − 1] contains the i − 1
smallest elements of the original A, in sorted order, and A[i : n] contains the rest.

Problem 3 : Correctness subtleties: duplicates and stability
 (a) The lecture assumes all elements of A are distinct. If instead A = [3, 1, 3, 2] has duplicates,
     does BUBBLESORT still sort it correctly?

 (b) A sort is stable if elements that compare equal keep their original relative order. This means
     that if one equal element appeared before another in the input, it must still appear before it
     in the output. For example, suppose the input has two elements with the same value, say two
     4’s, and we temporarily label them 4a (the one that appears first, further left) and 4b (the
     one that appears second) just so we can tell them apart. A stable sort is required to output
     them in the order . . . , 4a , . . . , 4b , . . .. In other words, it is never allowed to output 4b before
     4a , even though from the sort’s perspective the two values are tied and either order would
     technically still count as sorted. Is this version of BUBBLESORT stable? Justify using line 3
     specifically.


 Solution. (a) Yes, it still sorts correctly ([3, 1, 3, 2] → [1, 2, 3, 3]).

        (b) Yes, stable. Line 3 swaps only when A[j] < A[j − 1] (strict), so two adjacent equal

    relative order changed by being swapped directly past each other (not past a third, different
    element), and that never happens, their original relative order is preserved throughout. (Using
    ≤ instead would still sort correctly but could break stability.)


Problem 4 : Modifying the algorithm
    (a) Modify the BUBBLESORT algorithm so that it stops as soon as a full inner-loop pass makes no
        swaps. Give the modified pseudocode, and state the best-case running time (as a function
        of n) and on what kind of input it’s achieved. Compare to the unoptimized best case from
        Problem 2(a).

 (b) Change a single line of the original pseudocode so BUBBLESORT sorts into non-increasing order
     instead. Explain why your change works, in terms of the loop invariant.


    Solution. (a)
     1   BUBBLESORT - OPT (A , n )
     2   1 for i = 1 to n - 1
     3   2      swapped = FALSE
     4   3      for j = n downto i + 1
     5   4            if A [ j ] < A [ j - 1]
     6   5                 exchange A [ j ] with A [ j - 1]
     7   6                 swapped = TRUE
     8   7      if swapped == FALSE
     9   8            return

    Best case: already-sorted input. The very first pass (i = 1) does n − 1 comparisons, finds no
    swaps, and returns which is O(n), linear. This beats the unoptimized version, which always
    does n(n − 1)/2 = Θ(n2 ) comparisons no matter the input (Problem 2(a)), since it has no way
    to detect that no work remains.
        (b) Change line 3 to if A[j] > A[j-1]. The original invariant relies on bubbling the
    smallest remaining element into position i each outer iteration. Flipping the comparison flips
    which element “wins” each swap, so now the largest remaining element gets bubbled into
    position i instead. The invariant becomes: A[1 : i − 1] holds the i − 1 largest elements, in
    non-increasing order. At termination the whole array is sorted largest to smallest.


Problem 5 : Debugging via the invariant
A student proposes reversing the inner loop’s direction:
1    BUBBLESORT - BAD (A , n )


                                                    3
2    1       for i = 1 to n - 1
3    2           for j = i + 1 to n
4    3               if A [ j ] < A [ j - 1]
5    4                    exchange A [ j ] with A [ j - 1]


    (a) Find an input on which this does not sort correctly, and trace it to show the bug.
(b) Explain in terms of the loop invariant why running j upward (instead of downward) breaks
    correctness. What does the original inner loop accomplish that this version fails to?


    Solution. (a) Try A = [2, 3, 1], n = 3. i = 1: j = 2: A[2]=3 vs A[1]=2, not less, no swap;
    j = 3: A[3]=1 vs A[2]=3, 1 < 3, swap → [2, 1, 3]. i = 2: j = 3: A[3]=3 vs A[2]=1, not less, no
    swap. Final: [2, 1, 3] which is not sorted.
        (b) In the original (downward) version, j counts down from n to i + 1. As shown in
    the Lecture 1 correctness proof, whichever value is the true minimum of A[i : n] gets “picked
    up” the moment j reaches it (compared against something larger immediately to its left) and
    then keeps winning every subsequent comparison as j keeps decreasing — sliding one position
    further left on each remaining step of the pass — until j reaches i + 1 and the minimum lands
    in position i. So position i’s final value is the result of a whole chain of comparisons, against
    every element of A[i : n] that lay between the minimum’s original position and position i.
        In the modified (upward) version, j counts up from i + 1 to n. Position i is only ever
    involved in the very first comparison of the pass (when j = i + 1, comparing A[i + 1] against
    A[i]) and is never touched again. Once j advances to i + 2, i + 3, . . ., index i is behind the scan
    and is simply left alone. So whatever ends up at position i is just min(A[i], A[i + 1]), using only
    the two elements that started there. It has no mechanism for “finding out” that some smaller
    value might be sitting further right, at position i + 2 or beyond, because that comparison never
    happens.
        This is exactly the bug in the trace above: with A = [2, 3, 1], i = 1, the pass compares
    A[2] = 3 against A[1] = 2, finds 3 ̸< 2, and then moves on to j = 3 which leaves position 1
    alone for the rest of the pass. But the true minimum of A[1 : 3] is 1, sitting at position 3, and
    position 1 is never compared against it. The invariant “A[1 : i − 1] holds the i − 1 smallest
    elements, sorted” therefore fails to be established at i = 2, which is why the final array comes
    out unsorted.
